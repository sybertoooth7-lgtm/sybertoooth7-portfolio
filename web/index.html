§1 One case study, in full

ALUXPLAZA — Node 24, Express 5, PostgreSQL, React 19

The problem it exists for

Small and mid-size businesses in East Africa carry the same obligations as everyone else — PCI DSS, the Kenya Data Protection Act 2019, incident-response practice per NIST SP 800-61 — without the budget for a retained consultancy to tell them where they stand. The usual outcome is an assessment delivered as a PDF that nobody re-reads and that is out of date the week it lands.

What I built instead

A platform that keeps the assessment running. Clients sign up with verified email, work a compliance checklist against multiple frameworks, and get a computed risk score with a shareable verification link a third party can check without an account. On the other side, an operations console shows platform-wide compliance, per-client risk, contact triage, active IP blocks with one-click unblock, and a filterable security-event feed.

  • Two authorisation contexts, deliberately separated — admin and client tokens never share a cookie.
  • Attack traffic is detected, logged and scored by the platform itself, not by a SaaS bolted on the front.
  • Rate limiting and queueing run on Postgres. One datastore; no Redis to operate or bill for.
  • Ten written service methodologies and the client deliverable templates ship in docs/.

Stack — Express 5 (ESM), PostgreSQL, pg-boss, JWT with double-submit CSRF, helmet, pino, React 19, Vite, TypeScript, Tailwind, Vitest + supertest, Sentry.

§2 How the platform defends itself

a product that sells security has to run on it

These are the mechanisms that exist in the code today, each with the path a reviewer would open. Nothing here is a diagram of intent.

Request scanner, in-house
A five-module shield inspects every request: signature detector, IP blocklist, brute-force guard, event logger, and a risk score that turns observed abuse into a number an admin can act on. backend/src/shield/{detector,blocklist,bruteForceGuard,eventLogger,riskScore}.js
Split token contexts
Two cookies — adminToken and clientToken — so a client credential cannot be replayed against an admin route. Token confusion is structurally impossible rather than forbidden by policy. README.md § Features · backend middleware
CSRF and authentication hardening
Double-submit-cookie CSRF, bcrypt password hashing, account lockout with escalating timeouts, and authentication responses that do not leak whether an account exists. SECURITY_ARCHITECTURE.md § Trust Boundaries
Rate limiting without Redis
Limits are enforced in Postgres, so the constraint survives a restart and one service holds both state and quota. Boot-time configuration validation refuses weak signing secrets — 32 characters minimum, no dictionary words. backend/src/lib · backend/src/config.js
Audit trail as a surface, not a file
Middleware-level audit and login logging feed a filterable security-events view, so "what happened, to whom, when" is answerable without a log-aggregation vendor. backend/src/middleware · AdminSecurity.tsx
Pipeline guards
CodeQL SAST and gitleaks secret scanning run as dedicated workflows alongside split backend and frontend CI, so a broken API check cannot hide a broken UI build. .github/workflows/{ci,backend-ci,frontend-ci,codeql,gitleaks}.yml

§5 Services on offer

each one is a document before it is a script

Ten methodology documents sit in docs/, and each is a service I can take on. The short definition below is quoted from the document itself, not rewritten for marketing.

Table 3. "What this service actually is", verbatim openings from each methodology.
ServiceAs written in the repositoryScript
Access-control & authentication audit “A structured review of how a website or web app handles login, sessions, and access control … No AI theater, no invented scores. Every finding in the report is something the client (or anyone else) can independently reproduce and verify.” auth_audit.py
Network hardening review “A review of what a client's domain/servers expose to the internet … Every finding comes from a real, capped, passive TCP connection or DNS lookup, not a simulated AI scan.” network_audit.py
Vulnerability assessment “A scan of a client's live site for concrete, checkable exposure … Findings are aggregated into a transparent, explainable risk score — a simple weighted sum the client can verify by hand, not an opaque ‘AI prediction.’” vuln_assessment.py
Backup & encryption review “A review of how a client stores and backs up sensitive data … Every finding is backed by a real, reproducible check: a file permission read, a functional password-protection test on an archive, or a real HTTP request — never a simulated score.” backup_audit.py
Incident response planning “A written, client-specific IR plan: what to do, in what order, and who does it, if the client's site/systems are breached. This is not automation — no AI ‘orchestrates containment.’ It's a document a real human follows during a real bad day.” document only
Honeypot monitoring “Decoy routes no legitimate user would ever request — fake admin panels, fake .env files, common scanner targets … Because these routes have zero legitimate traffic, a hit is a strong, honest signal. This is a decades-old technique, not artificial intelligence.” honeypot.js
Threat-intelligence briefing “A periodic written briefing that aggregates real threat trends relevant to a specific client's industry — sourced from actual vendor threat reports and government advisories, not a fictional ‘federated AI network.’ Every claim traces to a named, dated source.” research

§6 The template behind each one

all ten documents follow the same skeleton, on purpose

I did not design this to look consistent. I designed it so that I cannot sell a service without writing down, in the same place every time, where the service stops. Nine of the ten documents carry the last two headings; all ten carry the first three.

  1. What this service actually is — one paragraph, no category claims.
  2. Who it's for — the business size and stack where the checks mean something.
  3. Scope of a typical engagement — bounded, so the quote means something.
  4. What the deliverable contains — the actual file, named.
  5. What requires manual review — four documents say the non-automatable part is the product.
  6. Framing this honestly to clients — present in nine of ten.
  7. Suggested starting price point — present in nine of ten.
  8. Legal & ethical guardrails — written to be run only against systems you own or hold explicit written authorisation to test.

“Never claim 100% security — flag genuine unknowns as unknowns rather than assuming compliance.”

backup-encryption-methodology.md

“This is the least urgent of the services on offer — say so. A client's limited security budget is almost always better spent on Access Control, Network Hardening, or the Vulnerability Assessment first.”

pqc-readiness-methodology.md

“Don't oversell ‘response time’ numbers — a plan followed by a human takes as long as it takes; there's no fictional ‘12ms response.’”

incident-response-service-methodology.md

How the pricing is written up

The documents deliberately fix the shape of the fee and leave the number for the call, because a number written before the scope is known is a guess dressed as a quote.

Access-control audit
A single small site — one login system, no complex RBAC — is a fixed-scope engagement, priced as a flat deliverable rather than hourly, so the cost is known up front.
Compliance readiness
Follow-up re-checks after remediation are priced as a smaller fixed add-on.
Incident response
The optional tabletop session is priced separately as a follow-on, since it is more time-intensive and higher-value than the document itself.
Threat intelligence
A flat fee per briefing, or a lower recurring quarterly retainer for ongoing coverage. The fee reflects research time — typically a few hours per briefing for a well-scoped industry — not a “live AI monitoring” premium.

§10 What I'd tell a client is still weak

self-reported, from my own threat model

A security engineer who says their system is finished is the one to avoid. SECURITY_ARCHITECTURE.md is a roadmap I wrote against my own build, and these are the open items on it, with the phase I assigned them.

Phase 1, critical — the token blocklist lives in memory
Ephemeral state. Revocation does not survive a restart and cannot scale horizontally. This is the one that would fail a production review first.
Phase 2, operational — alert fatigue and stale security state
Event noise is not tuned and old state is not reaped in the background, so the console shows everything with equal confidence.
Phase 3 — distributed attack detection is observe-only
The shield detects and logs, but does not coordinate a block across instances.
Phase 4, architectural — no request correlation or tracing
Events cannot yet be stitched into one attack narrative by trace ID.
Off the roadmap — CI is red on main right now
Two of the five workflows fail, and they were failing before the commit this page pins, so this is not a docs-edit regression. lint, typecheck and test-backend pass; format fails because prettier --check . flags seven files — a formatting debt, not broken code — and audit fails npm audit --audit-level=high on the frontend with 11 advisories, 8 of them high. Almost all of those are transitive, arriving through the Tailwind/PostCSS chain plus serialize-javascript and source-map-js. Most clear with npm audit fix; one needs a breaking Tailwind 4 jump, which is why it is still open instead of merged in a hurry. A reviewer who clicks the badge will find this in under a minute, which is why it is here.

Also honest: middleware ordering is not made explicit, and formal security regression tests are a named gap rather than a solved one. Nothing in the 26 test files exercises a distributed block or a trace ID — see §4.
