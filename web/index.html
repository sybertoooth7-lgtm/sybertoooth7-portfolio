01

Case study — ALUXPLAZA

full stack · Node 24 · React 19

The problem

Small and mid-size businesses in East Africa are expected to meet the same obligations as everyone else — PCI DSS, the Kenya Data Protection Act 2019, incident-response practice per NIST SP 800-61 — but can't afford a retained consultancy to tell them where they stand. The assessment ends up as a PDF nobody re-reads.

What I built

A platform that keeps the assessment live. Clients sign up with verified email, work a compliance checklist against multiple frameworks, and get a computed risk score with a shareable verification link that a third party can check without an account. On the other side, an admin console shows platform-wide compliance, per-client risk, contact triage, active IP blocks with one-click unblock, and a filterable security-event feed.

  • Two authorisation contexts, deliberately separated — admin and client tokens never share a cookie.
  • Attack traffic is detected, logged and scored by the platform itself, not a SaaS bolted on the front.
  • Rate limiting and queueing run on Postgres. One datastore, no Redis to operate or bill for.
  • Ten written service methodologies and client deliverable templates ship in docs/.

What is not claimed

The document states plainly that nothing in it is a legal opinion or a certification, and that any client or regulator use must first be reviewed by a qualified Kenyan data-protection lawyer.

What is not verified

The state of the production database. The migration runner applies migrations at boot, so 026–029 should run on the next deploy — and the document refuses to record that as confirmed.

What it does not cover

Whether registration with the ODPC is required, any lawful-basis decision, DPIA conclusions, certification, a production threat model. Those need a lawyer, the regulator, or a proper assessment.

Security posture — how it defends itself

the platform sells security, so it runs on it

Request scanner, in-house

A five-module shield inspects every request: signature detector, IP blocklist, brute-force guard, event logger and a risk score that turns observed abuse into a number an admin can act on.

backend/src/shield/{detector,blocklist,bruteForceGuard,eventLogger,riskScore}.js

Split token contexts

Two cookies — adminToken and clientToken — so a client credential can never be replayed against an admin route, and token confusion is structurally impossible rather than policy-enforced.

README.md § Features · backend middleware

CSRF + auth hardening

Double-submit-cookie CSRF, bcrypt password hashing, account lockout with escalating timeouts, and authentication responses that don't leak whether an account exists.

SECURITY_ARCHITECTURE.md § Trust Boundaries

Rate limiting without Redis

Limits are enforced in Postgres, so the constraint survives a restart and one service holds both state and quota. Boot-time config validation refuses weak signing secrets (≥32 chars, no dictionary words).

backend/src/lib · backend/src/config.js

Audit trail as a first-class surface

Middleware-level audit and login logging feed a filterable security-events view, so “what happened and to whom” is answerable without a log-aggregation vendor.

backend/src/middleware · AdminSecurity.tsx

Pipeline guards

CodeQL SAST and gitleaks secret scanning run as dedicated workflows alongside split backend and frontend CI — a broken API check doesn't hide a broken UI build, or the other way round.

.github/workflows/{ci,backend-ci,frontend-ci,codeql,gitleaks}.yml

What I'd tell a client is still weak

self-reported, from my own threat model

A security engineer who says their system is finished is the one to avoid. SECURITY_ARCHITECTURE.md is a roadmap I wrote against my own build, and these are the open items on it:

Distributed attack detection is observe-only

The shield detects and logs, but doesn't yet coordinate a block across instances. Phase 3 on the roadmap.

No request correlation or tracing

Events can't be stitched into one attack narrative by trace ID yet. Phase 4, architectural.

Token blocklist lives in memory

Ephemeral state — revocation doesn't survive a restart or scale horizontally. Phase 1, critical.

Alert fatigue & stale security state

Event noise isn't tuned and old state isn't reaped in the background. Phase 2, operational.

Also honest: middleware ordering isn't made explicit, and formal security regression tests are a named gap rather than a solved one.
